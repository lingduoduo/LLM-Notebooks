# Agent End-to-End Cost Analysis 

This project performs a full cost decomposition for a multi-turn agent workflow (refund handling), including input/cache/output tokens, latency, and cost distribution. It enables practical measurement of where costs come from and how optimization strategies affect total spend.

### What it does

The benchmark runs a fixed 8-turn customer refund scenario and records every LLM call with a lightweight tracing layer:
- token usage (prompt, cached prompt, output)
- latency
- model cost by pricing table

It then reports:
- per-step cost breakdown
- cost component breakdown (non-cached input / cached input / output)
- p50/p95/p99 for per-step cost
- full 2×2 A/B comparison between optimization levers

The two levers are:
- **KV-cache friendliness**: keep a stable prefix to maximize cache hits
- **Context compression**: summarize long tool outputs for earlier turns

### Scenario and benchmark invariants

The scenario is an English CloudShop refund case settled in CNY: order `ORD20240517001`, list price CNY 499, actual paid **CNY 469** after a coupon, refunded in full because the defect policy waives the restocking fee. The manual-approval threshold in the system prompt is CNY 500.

Three invariants are enforced by `test_benchmark_invariants.py` and re-checked at the start of every `run_scenario` call via `agent.validate_benchmark()`:

- The stable system prompt measures at least **1,024** tokens under the benchmark tokenizer (`agent.MIN_CACHEABLE_PREFIX_TOKENS`). Below that, providers will not cache the repeated prefix and the `kv` / `both` scenarios silently collapse into their uncached counterparts.
- Every entry in `TOOL_RESULTS` parses as a JSON object, since the raw text is fed to the model as a tool result.
- Commerce amounts stay in CNY; no dollar amounts appear in the prompt or the summaries.

### Default model and API behavior

- Default model: `gpt-5.6-luna`.
- Preferred credentials: `OPENAI_API_KEY`, fallback to `OPENROUTER_API_KEY` (`gpt-*` remapped to `openai/*`).
- If OpenRouter keys exist for `gpt-5.x`, it is preferred due to authentication requirements.
- Offline mode is supported via `sample_trace.json` so all tables can be recomputed without API calls, deterministically and without credentials.

### Files

| File | Purpose |
|---|---|
| `config.py` | pricing model definitions and pricing presets |
| `tracer.py` | tracing helper and cost decomposition/aggregation |
| `agent.py` | 8-turn refund agent with `run_scenario(kv_cache, compress)` |

### Run

```bash
pip install -r requirements.txt

export OPENAI_API_KEY=sk-...   # or OPENROUTER_API_KEY=sk-or-...
python demo.py
python demo.py --offline --scenario all
```

### CLI options

| Argument | Meaning |
|---|---|
| `--live` / `--offline` | call real model (default) / recompute from trace |
| `--scenario` | `ab` (naive+both), `all` (four scenarios), or subset list |
| `--trace` | trace file for offline mode |
| `--save-trace` | persist observed token usage from online runs |
| `--model` | model name for price preset |
| `--price-input` / `--price-cached` / `--price-output` | override per-million-token prices |
| `--no-warmup` | disable prefix warmup for KV-cache scenario |
| `--output` | export full result JSON |

### A/B scenarios (2×2)

| Scenario | KV-cache | Compression | Context design |
|---|---|---|---|
| `naive` | no | no | random session header + full tool returns |
| `kv` | yes | no | stable long prefix |
| `compress` | no | yes | only keep last 2 turns full; older turns summarized |
| `both` | yes | yes | stable prefix + compressed history |

The task logic is identical across scenarios so differences isolate optimization effects.

### Interpretation

- KV-cache can produce large improvements when prefixes are stable.
- Compression lowers prompt growth while keeping functional behavior.
- Joint optimization usually gives best total cost, though cache gains and compression gains are not simply additive.

Live mode is the only mode that produces **observed** measurements. Offline numbers illustrate the mechanism; they are not evidence of what a given provider will bill you.

### Provenance: live vs. offline

Every trace carries a `provenance` field, and both modes print it.

| Mode | `provenance` | What the numbers are |
|---|---|---|
| `--live` (with `--save-trace`) | `observed` | token usage reported by the provider during real model calls |
| `--offline` with the bundled `sample_trace.json` | `synthetic` | deterministic values generated from the fixtures — **not** a recording of a live run |

The bundled trace is generated by `make_sample_trace.py`:

- **Input side is derived, not invented.** Prompt and tool-context token counts come from tokenizing the actual English fixtures through the same four message-building strategies the benchmark uses. Cached counts come from a declared cache model: the verbatim common prefix between consecutive requests, block-aligned to 128 tokens, zero below the 1,024-token minimum, and never above that turn's prompt count.
- **Output side is a fixed constant.** Completion tokens and latency are fixed synthetic values, identical across all four scenarios, so the A/B comparison isolates input-token effects. Inventing per-call generation variance would mean fabricating measurements.

Regenerate it after changing the system prompt, tool fixtures, or summaries:

```bash
python make_sample_trace.py
```

### Offline recomputation

Offline mode reads a trace and re-runs only the cost arithmetic, enabling:
- quick replication without keys
- quick "what-if" with different model prices

To recompute against your own measurements instead of the synthetic bundle, capture a trace first:

```bash
python demo.py --live --scenario all --save-trace my_trace.json
python demo.py --offline --trace my_trace.json --model gpt-4o
```

### Notes

- Live numbers vary with real API behavior and cache timing; the bundled offline trace does not vary at all.
- Prompt cache is best-effort and may miss in some turns, so live cache rates can fall below the synthetic model's.
- Tool-return token estimate uses tokenizer counts against the current model encoder.
- Key precedence: prefer `OPENAI_API_KEY`; fallback is automatic via OpenRouter for supported paths. If `OPENROUTER_API_KEY` is set and the model is `gpt-5.x`, the OpenRouter route wins.
- `COST_DEMO_MODEL` sets the default model; `--model` overrides it for a single run and selects the price preset.
