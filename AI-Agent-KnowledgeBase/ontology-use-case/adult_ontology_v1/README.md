# Room taxonomy and ontology v1.3

A versioned, multi-label taxonomy for room subjects and up to five tags. The
hierarchy has L1 categories, L2 concept groups and L3 specific concepts; the
optional `adult_content` umbrella is L0 for content categories only.

| Category code | Axis | Stable L1 concept ID | L2 groups | Example L3 concepts |
| --- | --- | --- | --- | --- |
| `BODY` | content | `body_appearance` | Nudity, clothing, appearance | Full nudity, partial nudity, lingerie, costume |
| `ACT` | content | `sexual_activities` | Solo, partnered, intimacy | Solo performance, partnered intimacy |
| `KINK` | content | `fetish_kink` | BDSM, roleplay, material interests | Bondage, dominance, submission, latex |
| `FORMAT` | format | `performance_format` | Broadcast mode, interaction | Public live, private show, group show |
| `PRODUCT` | content | `products_props` | Devices, accessories | Adult toy, interactive device, restraints |
| `SOCIAL` | interaction | `social_interaction` | Conversation, engagement | Flirting, chat, audience requests |
| `IDENTITY` | identity | `identity_audience` | Self-description, audience | Gender identity, orientation, audience interest |
| `COMMERCE` | commerce | `commercial_context` | Payments, promotions | Tips, subscription, paid session, tip goal |
| `GENERIC` | generic | `generic_reference` | Explicit reference, crude language, media reference, unrelated | Explicit (general), profanity, crude slang, brand, shock meme, other |

## Modeling decisions

- **Independent dimensions stay separate.** Each category belongs to one axis.
  Only `content` categories are `IS_A adult_content`; FORMAT, SOCIAL, IDENTITY,
  COMMERCE and GENERIC are standalone L1 roots. A private show is a format and a tip goal
  is monetization; neither implies adult content or a sexual activity.
- **Identity descriptors are neutral.** IDENTITY is its own axis, never under the
  content root, and the room API accepts it only by explicit self-declaration.
  Orientation or gender identity does not imply explicit content.
- **Safety classification is separate.** Consent, exploitation, age-related
  concerns and policy violations are not modeled here. The validator accepts
  only the six axes above, so policy labels cannot be added to this taxonomy;
  they belong in a separate policy-label system with additional safeguards.
  `requires_context_review` flags ambiguous keywords, not policy outcomes.

Codes identify categories; existing concept IDs remain canonical. Each L1–L3
node carries its category code in `category_id`; L0 has `category_id: null`.
For example, `lingerie → clothing → body_appearance` all carry `BODY`. Keep
IDs unchanged when labels or parents change, and never reuse retired IDs for
different concepts. Reparenting across categories requires updating the subtree's
category metadata and corresponding edges. A room can hold assignments from
several branches even though each taxonomy concept has one parent.

## Vocabulary

All keywords live in one file, `keywords_v1.csv` (353 rows). `load()` reads it
and rejects a keyword mapped to the same concept twice. The `source` column
records provenance:

| `source` | Rows | Origin | Maintained by |
| --- | --- | --- | --- |
| `curated_seed` | 25 | `SEEDS` in `build.py` | Regenerated by `--init` |
| `ldnoobw_en` | 328 | Mapped English [LDNOOBW](https://github.com/LDNOOBW/List-of-Dirty-Naughty-Obscene-and-Otherwise-Bad-Words) terms (CC BY 4.0) | Curated; preserved verbatim by `--init` |

`--init` rewrites only the `curated_seed` rows and keeps every other row, so
reviewed imports can be appended to the same file. `policy_candidates_ldnoobw_en.csv`
(69 rows) is **not vocabulary**: it is routed to the separate policy-label
system and never loaded by the matcher.

All 403 English LDNOOBW entries are accounted for. The six already in the seed
(nude, nudity, topless, bdsm, bondage, domination) are not duplicated. Each other
term maps to the most closely related existing concept. Anatomy maps to the
`nudity` L2 group, explicit acts to `partnered_activity`, `self_stimulation` or
the `sexual_activities` L1, fetishes without a specific concept to the
`fetish_kink` L1, and toys to `adult_toy`. Ambiguous terms (for example `ass`,
`snowballing`, `bareback`, `sexy`) keep that mapping with
`context_required: true`; 112 rows are flagged. Terms with no related concept go
to GENERIC: generic explicitness (`porn`, `xxx`), profanity, crude slang, brand
and site names, shock memes and unrelated words (`viagra`). GENERIC is its own
axis, so these never imply `adult_content`. No term is mapped to IDENTITY.
Every imported row has `review_status: mapped_unreviewed`.

Terms indicating minors, non-consent, bestiality, incest, violence or extremism,
solicitation, and slurs are kept out of the taxonomy (modeling decision 3).
They are listed with a `policy_route` in `policy_candidates_ldnoobw_en.csv`,
which the matcher never loads. A test asserts no policy term is also a keyword.

Matching uses whole-word boundaries, so `class`, `Assassin` and `Scunthorpe`
do not match `ass` or `cunt`. With 353 keywords a reused matcher classifies
1,000 short records in about 39 ms locally (12 ms with the 25 seed keywords).

Importing a dictionary creates `candidate_terms.csv` with *unmapped* terms. Review and assign sexual-content concept IDs before adding terms to `keywords_v1.csv`. This prevents profanity, identity words, and benign ambiguous terms from being automatically treated as adult content.

## Files

- `taxonomy_v1.json`: concept nodes and IS_A edges.
- `taxonomy_schema.json`: JSON Schema for taxonomy file.
- `keywords_v1.csv`: the single keyword vocabulary: illustrative seed terms plus mapped LDNOOBW terms (see Vocabulary); not a comprehensive NSFW list.
- `policy_candidates_ldnoobw_en.csv`: LDNOOBW terms routed to policy review; never matched.
- `sample_output.json`: sample classifier output.
- `build.py`: generator, compatibility exports, CLI, and candidate importer.
- `taxonomy.py`: category metadata, schema builder and graph validation.
- `matching.py`: prepared keyword matching (the existing API).
- `room_classifier.py`: versioned room assignments and distinct-room aggregation.
- `sample_room_output.json`: evidence-backed room classification example.

## Limitations

This is a deterministic baseline, not a trained classifier. Keyword matches are evidence, not calibrated probabilities. It supports Unicode NFKC/casefold but does not handle morphology, misspellings, obfuscation, multi-language segmentation, negation, or semantic disambiguation. For production, add language-specific tokenization, review, provenance, evaluation, and a separate safety/policy layer.

## Classify a batch

Load files and prepare a matcher once, then reuse it across records:

```python
from build import Matcher, load

parents, rows = load()
matcher = Matcher(parents, rows)
result = matcher.match('Private show with cosplay', ['bdsm', 'lingerie'])
```

Preparation normalizes keywords, compiles their boundary patterns, and resolves
ancestor sets. Output order, Unicode normalization, overlapping keyword matches,
and the five-tag limit are preserved. The existing
`match(subject, tags, parents, rows)` function remains available for single calls;
it prepares a new matcher each time. Construct a new matcher after editing the
ontology or vocabulary.

Invalid parent references, cycles, duplicate node IDs when loading, empty keywords,
unknown keyword concepts, and invalid `context_required` flags raise `ValueError`.
`load_taxonomy()` additionally validates L0–L3 levels, the eight L1 category
codes, inherited category membership, parent references and exact agreement
between `IS_A` edges and parents. The generated JSON Schema describes the file
structure; the runtime graph checks enforce relationships across nodes.

A historical comparison over 1,000 generated records using the original 22 keywords
produced identical results to the original implementation. Best of five runs:
original 71 ms, reused matcher 28 ms (approximately 2.5× faster), compatibility
wrapper 68 ms. These measurements exclude file loading and matcher preparation
for the reusable path; throughput depends on text length and vocabulary size.
Matching still visits every keyword for each field, but runs the boundary regex
only when the keyword occurs as a substring. Over 5,000 randomized records this
gave identical output and cut a reused-matcher batch of 1,000 from 38 ms to
12 ms (approximately 3.2× faster). Cached ancestor sets use
memory proportional to the sum of node depths, which suits this small taxonomy.

## Versioned room classification

```python
from build import RoomClassifier, count_rooms_by_category, load, load_taxonomy

_, rows = load()
classifier = RoomClassifier(load_taxonomy(), rows)
room = classifier.classify_room(
    'room_123', 'Private show with cosplay and latex', ['latex']
)
counts = count_rooms_by_category([room])
# counts['FORMAT'] == 1; counts['KINK'] == 1, despite several KINK concepts.
```

Each result includes `taxonomy_version`, one assignment per directly supported
concept, `category_ids`, `axes`, inferred ancestors and context-review flags.
Each assignment carries its `axis`. Assignments
retain all supporting fields: `text` is the complete original field, and
`matched_term` is the normalized keyword. These are evidence records, not exact
character offsets or calibrated probabilities. Ambiguous matches retain
`requires_context_review: true`; downstream review decides whether to accept them.
`bdsm` can be assigned at L2 without inventing any L3 descendants. `cosplay`
does not imply nudity or sexual activity.

The room API ignores keyword-derived IDENTITY concepts. Use the explicit
`self_declared_concepts=['orientation']` argument to record a self-declared
identity concept; it accepts only IDs from the IDENTITY branch. This API records
the concept, not a specific personal identity value. The application must obtain
the declaration from the room owner. Identity and audience descriptions are not
safety classifications. The lower-level legacy `Matcher` remains a generic
keyword-evidence extractor and does not enforce this room-assignment rule.

`count_rooms_by_category` counts distinct `room_id` values per category, including
assignments still needing context review. Duplicate room records are unioned;
select the desired snapshot before calling it. It rejects mixed taxonomy versions.

The taxonomy release is `1.3.0`. Compatibility filenames (`taxonomy_v1.json`,
`keywords_v1.csv`) and existing concept IDs are retained. Release 1.3.0 adds the
standalone GENERIC category (`generic` axis) and the mapped LDNOOBW vocabulary.
Release 1.2.0 assigned
each category an axis, detaches the four non-content categories from
`adult_content`, adds `tip_goal` under COMMERCE → Payments and maps the keyword
`tip goal` to it instead of `goal_show`. Room results from 1.1.0 inferred
`adult_content` for every assignment; recompute them rather than aggregating
across versions. Release 1.1.0 added `intimacy` and `chat`, reparented
`partnered_intimacy` under `intimacy`, and updated display labels. Save each taxonomy release (for example in
version control) with historical room results; recompute derived ancestors after
an intentional migration. Older taxonomy files need `category_id` metadata and
per-category axes before the current validator can load them. `--init` rebuilds the supplied
fixtures and overwrites the taxonomy and the seed vocabulary rows (other
`keywords_v1.csv` rows are kept), so preserve local edits before using it.

## Semantic evaluation

Borrowed dataset-design ideas are documented in [evaluation/README.md](evaluation/README.md)
with public card references and licensing/provenance observations. The bundled
28-case fixture is original text, not imported Hugging Face rows. It exercises
paraphrases, negation, benign meanings and multi-axis labels against independent
gold. No taxonomy, vocabulary or policy behavior changes for this benchmark.

```bash
python semantic_evaluation.py --output /tmp/room-evaluation.json
python semantic_evaluation.py --predictions /path/to/model-predictions.jsonl
```

Reports include concept/category/hierarchical scores, per-label and per-slice
metrics, candidate false positives on taxonomy-negative text, review flags and
per-case errors. The keyword baseline is not a semantic model; flags requiring
review do not establish semantic correctness. External semantic-model predictions
can be compared using the same fixture without making API calls in this tool.

## Candidate import memory

Dictionary files are read one line at a time. Deduplication retains one key per
unique `(keyword, language)` pair; the full input file is no longer retained.
A local 400,000-line input containing repeated terms produced byte-identical CSV
output with peak Python-traced memory reduced from 34.42 MiB to 0.42 MiB. Unique
vocabularies still require memory proportional to their unique term count.
Unicode line separators remain supported. Importing the destination
`candidate_terms.csv` itself (including filesystem aliases) raises `ValueError`.
Imports append incrementally; an interrupted import may retain completed rows,
and rerunning it deduplicates those rows.

## Related Spark SQL

`../social_follow_graph_spark.sql` computes shared-follower similarities and
recommendations. Its pair join generates `d * (d - 1) / 2` pairs for a user with
`d` follows. Temporary views are logical definitions, so the script caches the
two views read by several later steps: deduplicated `follow_edges` (one source
scan and shuffle instead of one per consumer) and `broadcaster_similarity` (the
quadratic pair join is computed once). On local Spark 4.1.1 with a synthetic
6,000-edge graph, every view matched the uncached script exactly and the script
re-ran cleanly in the same session. No runtime claims are made without a
representative dataset. Budget cache storage (it spills to disk) and `UNCACHE`
when the session finishes. Degree caps and approximate pair generation change
results and require an explicit quality/performance tradeoff.
